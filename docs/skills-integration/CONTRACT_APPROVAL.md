# Skills Security Audit contract approval

Status: owner-approved implementation contract; production activation remains
separately gated by `SKILLS_SECURITY_AUDIT_LIVE=false` by default and requires
Phase 3 qualification evidence.

## Approved schemas and negotiation

- `skills-audit/v1` is the canonical SDK schema. Approved event types are
  `skill_discovery`, `skill_authorization`, `skill_planning`,
  `skill_revocation`, `skill_validation_failed`, `skill_execution_rejected`,
  and `skill_plan_validated`. Outcomes are `allow`, `deny`, `success`, or
  `fail`.
- `policy-audit/v1` is a compatibility schema for the Policy Lane 3 contract at
  `afdf899`. It uses the existing AuditEvent envelope and receives Policy's
  strict five-field receipt projection. It is not inferred as
  `skills-audit/v1`.
- Unknown fields, event types, actions, outcomes, schemas, unbounded values,
  non-decimal tenant IDs, and tenant/workload mismatches are rejected.

The immutable approval reference is `skills-security-audit-contract/2026-10-29`.
Any field or vocabulary change requires a new schema version and approval.

## Redaction and pseudonymization

Payloads, inputs, outputs, prompts, credentials, tokens, signatures, free-text
clinical data, email addresses, URIs, and artifact paths are prohibited. Reason
fields accept bounded machine reason codes only. Principal identifiers are
opaque authority-issued pseudonymous identifiers; the sink never enriches them
with claims or profile data. Policy context is an exact allowlist of decision,
policy, enforcement, freshness, latency, and error-code evidence.

## Tenancy

Tenant identifiers are opaque decimal strings. They are validated as strings
of ASCII digits and are never parsed, normalized, or generated by this service.
The verified workload tenant must exactly match the event tenant. Durable rows
and receipts are partitioned by that exact string.

## Signing and rotation

Receipt signatures are Ed25519 over canonical bound receipt fields using a
runtime-injected private key. Only the public verification key is shared with
clients. Keys are never committed or logged. Every receipt carries `key_id`;
rotation assigns a new ID and retains old public verification material for the
full receipt retention period.

## Durability, idempotency, and retention

A durable receipt is returned only after the event and receipt rows commit in
one database transaction. The idempotency key must equal `event_id`. Repeating
identical canonical bytes returns the original receipt; reusing an ID for
different bytes is a conflict. A queue acknowledgement or local log is never a
durable receipt.

`AUDIT_RETENTION_DAYS` must be explicitly configured to at least 90 days before
the feature can be enabled. Receipt rows share the event retention and legal
hold boundary. The supported retry/reconciliation window is seven days, so the
approved minimum retention exceeds it. Legal holds always suppress deletion.
