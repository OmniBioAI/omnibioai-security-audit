# Skills Security Audit contract approval

Status: owner-approved implementation contract; production activation remains
separately gated by `SKILLS_SECURITY_AUDIT_LIVE=false` by default and requires
Phase 3 qualification evidence.

## Approved schemas and negotiation

- `skills-audit/v1` is the canonical SDK schema. Approved event types are
  `skill_discovery`, `skill_authorization`, `skill_planning`,
  `skill_revocation`, `skill_validation_failed`, `skill_execution_rejected`,
  and `skill_plan_validated`. Outcomes are `allow`, `deny`, `success`, or
  `fail`.
- `policy-audit/v1` is a compatibility schema for the Policy Lane 3 contract at
  `afdf899`. It uses the existing AuditEvent envelope and receives the same
  full signed canonical receipt as the SDK schema. It is not inferred as
  `skills-audit/v1`; Policy may project the verified receipt into its local
  five-field response only after signature verification.
- Unknown fields, event types, actions, outcomes, schemas, unbounded values,
  integer tenant IDs, non-canonical decimal tenant strings, and
  tenant/workload mismatches are rejected.

The immutable approval reference is `skills-security-audit-contract/2026-10-29`.
Any field or vocabulary change requires a new schema version and approval.

## Redaction and pseudonymization

Payloads, inputs, outputs, prompts, credentials, tokens, signatures, free-text
clinical data, email addresses, URIs, and artifact paths are prohibited. Reason
fields accept bounded machine reason codes only. Principal identifiers are
opaque authority-issued pseudonymous identifiers; the sink never enriches them
with claims or profile data. Policy context is an exact allowlist of decision,
policy, enforcement, freshness, latency, and error-code evidence.

## Tenancy

Tenant identifiers are opaque canonical decimal strings, such as `"42"`;
`"0"` is the canonical representation for zero. Integers, `"042"`, signs,
whitespace, and non-ASCII digits are rejected. IDs are never parsed,
normalized, or generated by this service. The verified workload tenant must
exactly match the event tenant. Durable rows and receipts are partitioned by
that exact string.

## Signing and rotation

The full `DurableAuditReceiptV1` is canonical and authoritative. Its wire
serialization is UTF-8 JSON with lexicographically sorted object keys, no
insignificant whitespace, unescaped Unicode, and values serialized exactly as
the schema's JSON-mode model dump (timestamps use ISO-8601 UTC `Z`). The
detached `signature` member is excluded only from the bytes being signed; every
other receipt field, including `event_id`, schema, durable timestamp, tenant,
partition, `key_id`, and `durable`, is included. The signature is
`ed25519:` plus unpadded base64url of the Ed25519 signature over
`b"omnibioai-security-audit-receipt-v1\x00" + canonical_json(fields)`. Here,
`canonical_json` is `json.dumps(fields, sort_keys=True, separators=(",", ":"),
ensure_ascii=False).encode("utf-8")`.

Consumers must validate the complete receipt schema, select a trusted public
key by `key_id`, remove only `signature`, serialize the remaining complete
receipt by the canonical rules above, and verify the detached Ed25519
signature before trusting any field. A consumer may then project fields into
its local API shape; it must never verify a projection or a subset. Only the
private signing key is injected at runtime; public verification keys may be
shared. Key material is never committed or logged. Rotation assigns a new ID
and retains old public verification material for the full receipt retention
period.

## Durability, idempotency, and retention

A durable receipt is returned only after the event and receipt rows commit in
one database transaction. The idempotency key must equal `event_id`. Repeating
identical canonical bytes returns the original receipt; reusing an ID for
different bytes is a conflict. A queue acknowledgement or local log is never a
durable receipt.

`AUDIT_RETENTION_DAYS` must be explicitly configured to at least 90 days before
the feature can be enabled. Receipt rows share the event retention and legal
hold boundary. The supported retry/reconciliation window is seven days, so the
approved minimum retention exceeds it. Legal holds always suppress deletion.
